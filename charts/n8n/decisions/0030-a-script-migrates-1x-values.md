# 0030. A script migrates a 1.x values file to 2.0

Date: 2026-11-03
PR: https://github.com/n8n-io/n8n-hosting/pull/288

## Context

Chart 2.0 retires many values keys, turns nine `extraEnv` lists into `env` maps, and runs n8n 3.0, which renames or removes some environment variables. Decision 0020 makes the render fail on every retired key and name its replacement. That tells a user what to change, but they still make every edit by hand, and most of the edits are mechanical.

## Decision

The chart includes `scripts/migrate-values.sh`, which reads a 1.x values file and writes a 2.0 values file, with a report on stderr. It follows `UPGRADING.md` row by row. Where `UPGRADING.md` leaves the choice to the user, the script keeps the 1.x behaviour and says so in the report. This sits under "Upgrades are in place, across majors included".

- It is a bash script on mikefarah's `yq` v4, a single binary that keeps most comments. Python with `ruamel.yaml` keeps comments better, but every user would have to install it first.
- It ships inside the chart, so `helm pull --untar` hands it over with the version it migrates to.
- It never reads Secret contents and never generates a secret, as the chart never does. Where a Secret needs a change, the report names it.
- It is idempotent. Running it over a 2.0 values file changes nothing.

CI runs every example from the previous major through the script and renders the result with the chart. The script's tests fail when `n8n.retiredKeys` names a key the script does not handle.

## Consequences

- An upgrade to 2.0 becomes a review of a diff rather than a hand edit.
- A change that retires a values key adds its transform to the script, with a test case, in the same change.
- Plain YAML only. Helmfile `.gotmpl` files and values generated by Argo CD or other templating are out of scope.
- `yq` rewrites some formatting, such as the spacing before an inline comment, so the diff can show lines the script did not change.
